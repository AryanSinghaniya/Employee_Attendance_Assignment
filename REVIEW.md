# REVIEW.md

Defects found in the starter `app/main.py`, verified against the rules in `openapi.yaml` and the starter code.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `_compute_late_minutes` (lines 97–99) | Floors elapsed time to whole minutes before checking `> 10`. R2 states late means strictly more than 10 minutes (600 seconds) after `shift_start`. Punch-in between 09:40:01 and 09:40:59 gave 10 minutes on floor division, which fails `> 10` and treats the punch as on time (`0`). | Shift 09:30, punch-in 09:40:01 returned `late_minutes = 0`; the R2 spec example requires 10. | Compared elapsed seconds directly: return 0 when `elapsed_seconds <= 600`. When late, return `int(elapsed_seconds // 60)`. |
| 2 | `_round_half_up` (lines 72–75), `_compute_work_hours` (lines 102–105) | Used float arithmetic `math.floor(value * factor + 0.5) / factor`. Due to binary float representation, some half-way values round down instead of up. R4 requires half-up rounding to two decimal places ("not float rounding"). | 522 seconds is 0.145 hours and must round to 0.15, but the starter returned 0.14. | In `_compute_work_hours`, computed hours directly from integer seconds via `(Decimal(seconds) / Decimal(3600)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. In `_round_half_up`, cleaned float noise with `round(value, 9)` and converted to `Decimal` with `ROUND_HALF_UP`. |
| 3 | `PunchInRequest`, `PunchOutRequest`, `RegularizeRequest` (lines 196, 214, 224, 225) | Epoch millisecond fields were typed as `Optional[int]`. In Pydantic v2, standard `int` coerces numeric strings (e.g. `"1791786000000"`) and floats (e.g. `1791786000000.0`). The spec requires rejecting strings and floats with 422. | Sending POST `/attendance/punch-in` with `"punched_at": "1791786000000"` returned 201 instead of 422. | Defined `StrictEpochMs = Annotated[StrictInt, Field(ge=EPOCH_MIN, le=EPOCH_MAX)]` and used it for `punched_at`, `punch_in`, and `punch_out`. |
| 4 | `EmployeeCreate.joined_on` (line 185) | Declared as bare `joined_on: str` with no format or calendar validation, so invalid dates like `"2026-13-45"` were accepted and stored. | POST `/employees` with `"joined_on": "2026-13-45"` returned 201. | Added regex pattern `r"^\d{4}-\d{2}-\d{2}$"` and a `@field_validator("joined_on")` that parses with `datetime.strptime(v, "%Y-%m-%d")`, raising a `ValueError` (FastAPI returns 422). |
| 5 | `punch_out()` (lines 316–322) | Queried only records with `punch_out: None`. If a matching record was already punched out, the query returned `None` and raised 404 instead of 409. Duplicate punch-outs or retries got 404. | Calling punch-out twice on the same record returned 404 on the second call instead of 409. | When the open-record query returns `None`, added a secondary lookup for any matching record with `punch_in <= punch_dt`. If found and its `punch_out` is not `None`, raised 409. Also kept atomic `find_one_and_update({"punch_out": None})` returning 409 if another worker closed it concurrently. |
| 6 | `employee_monthly`, `department_summary`, `late_leaderboard` (lines 486–510, 539–571, 601–615) | Pulled all matching documents into Python with `list(db.attendance_logs.find(...))` and computed sums, averages, and group counts in Python loops instead of running MongoDB aggregation pipelines. | Response times degrade linearly as attendance logs grow; memory footprint spikes on ~100k records; explain shows plain cursor finds. | Replaced Python loops with server-side MongoDB aggregation pipelines using `$match`, `$group`, `$lookup`, and `$project`. Moved pipeline definitions into dedicated builder functions: `_build_employee_monthly_pipeline`, `_build_department_summary_pipeline`, and `_build_late_leaderboard_pipeline`. Dense ranking (1, 2, 2, 4) for the leaderboard is calculated over the small aggregated result. |
| 7 | `department_trend` (lines 646–736) | While `$densify` was present in the starter for date generation, the pipeline was written inline without a reusable builder, leaving `/admin/explain` unable to inspect it. Furthermore, post-densify metrics (7-day moving averages and historical headcount) ran in a Python loop, and date parsing lacked error handling (HTTP 500 on bad dates). | `GET /analytics/departments/{dept}/trend` crashed with 500 when given invalid dates like `from=2026-13-01`; `/admin/explain/department_trend` explained an unrelated `find()` instead of this pipeline. | Extracted pipeline construction into `_build_department_trend_pipeline`, added calendar validation returning 422, and ensured `/admin/explain` runs the exact same aggregation pipeline via `db.command`. |
| 8 | `create_indexes()` (lines 33–44), `health()` (lines 240–245) | Startup index creation had no `try/except` block, crashing the app if MongoDB was momentarily unreachable at boot. Missing compound and single-field indexes needed for queries: `(date, late_minutes)` for leaderboard filtering, `(department, joined_on)` and standalone `joined_on` for headcount queries. Also, `/health` never retried index creation. | Booting the app when MongoDB is temporarily down causes an unhandled crash instead of a 503 from `/health`. Analytics queries on ~100k records perform COLLSCAN on missing index fields. | Wrapped `create_indexes()` in `try/except` so startup continues even if MongoDB is not immediately ready. Called `create_indexes()` inside `/health` after a successful `ping` so indexes are created on the first healthy probe. Added indexes `(date, late_minutes)`, `joined_on`, and `(department, joined_on)`. |
| 9 | `/admin/explain/{endpoint}` (lines 751–786) | Called `.explain("executionStats")` on plain `db.attendance_logs.find()` or `db.employees.find()` instead of running explain on the endpoint's actual aggregation pipeline. In PyMongo 4, `Cursor.explain()` also ignores verbosity parameters. | Explaining `department_summary` inspected a plain `employees.find()` query, giving misleading execution stats that did not reflect the real analytics pipeline. | Shared aggregation pipelines between endpoints and explain using builder functions: `_build_employee_monthly_pipeline`, `_build_department_summary_pipeline`, `_build_late_leaderboard_pipeline`, and `_build_department_trend_pipeline`. Executed explain using `db.command({"explain": {"aggregate": collection, "pipeline": pipeline, "cursor": {}}, "verbosity": "executionStats"})` via `_run_explain`. |
| 10 | `list_attendance` (lines 350–367), `regularize_attendance` (line 430), `department_trend` (lines 646–647) | Date inputs and status values were not validated. `date_from`, `date_to`, and `status` in `GET /attendance` accepted invalid strings or unknown statuses. Path parameter `date` in `PATCH /attendance` was unvalidated. In `department_trend`, unhandled `datetime.strptime` on invalid dates raised an uncaught `ValueError`, producing an HTTP 500 error instead of 422. | Calling `GET /attendance?status=INVALID` or `GET /analytics/departments/Eng/trend?from=2026-13-01&to=2026-07-10` returned 500 or allowed invalid queries through. | In `list_attendance`, validated `date_from` and `date_to` using `datetime.strptime` inside `try/except ValueError` returning 422, and validated `status` against `ALL_STATUSES` returning 422. In `regularize_attendance`, validated `date` with `datetime.strptime` returning 422. In `department_trend`, wrapped `from_` and `to` parsing in `try/except ValueError` returning 422. |

**Hardening, not defects:** the Mongo client now uses `tz_aware=True` so BSON dates come back as UTC-aware datetimes, and `load_dotenv(encoding="utf-8-sig")` tolerates a BOM in `.env` on Windows.
